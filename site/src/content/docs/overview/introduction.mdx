Envy creates temporary previews of microservice applications on Kubernetes with Istio or Cilium. The Linkerd adapter remains [blocked pending controller generation status](/getting-started/mesh-installation/). It deploys the services you change and reuses the rest from an approved running application.

Each preview gets a URL. Developers, CI workflows, and coding agents can create previews, wait for readiness, fetch log snapshots, and request cleanup through the `delivery` CLI, REST API, or MCP server.

## Three concepts

| Concept         | Meaning                                                                                                                                                        |
| :-------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Baseline**    | An approved deployed application with registered service addresses and a readiness check. It can represent `main`, a release, or another reference deployment. |
| **Override**    | A replacement container image for an approved service. Envy deploys it in a temporary namespace.                                                               |
| **Composition** | A preview that combines a baseline with one to three overrides, plus a URL and an expiry time.                                                                 |

## How a request reaches your change

For a change to `service-b`, the preview uses the existing gateway and `service-a`, then routes to your replacement `service-b`:

The preview ingress sets `baggage: composition=<id>`. Applications must forward that header on downstream HTTP calls. The selected mesh uses it to select the matching override; calls without matching composition context use the baseline.

Existing OpenTelemetry instrumentation can provide this propagation when configured for W3C Baggage on both incoming handlers and outgoing clients. See the [routing contract](/reference/routing/) for an example.

## What stays shared

Unchanged services, databases, caches, and external dependencies remain shared. **Writes from a preview can change baseline data.** Envy provides request routing and separate override workloads; it does not create an independent copy of application state.

This model suits integration testing against an existing reference application. Tests that require independent databases, destructive migrations, or isolated queue consumers need separate data and messaging arrangements. Read [Sharing & Isolation](/overview/sharing-semantics/) before onboarding an application.

## Preview lifecycle

1. Create a composition with approved images and a TTL (8 hours by default).
2. Wait until workload readiness, routing, and the declared ingress check succeed.
3. Run your own functional tests against the preview URL. Readiness confirms the configured check, not every application behavior.
4. Update images in place or request teardown. The reconciler also cleans up expired compositions.

The URL is allocated when creation is accepted. Time to readiness depends on image pulls, workload startup, routing, and verification.
