Envy creates temporary compositions of microservice applications on Kubernetes with Istio, Cilium, or Linkerd. It deploys the services you change and reuses the rest from an approved running application. HTTP compositions receive a preview URL; endpoint-free Jobs report execution lifecycle without an ingress route.

Each preview gets a URL. The optional [GitHub App](/integrations/github-app/) creates previews for labelled PRs, updates them from successful builds of the current head commit, and cleans them up when the label is removed, the PR closes, or the TTL expires. Developers, CI workflows, and coding agents can create previews, wait for readiness, fetch log snapshots, and request cleanup through the `envy` CLI, REST API, or MCP server.

## Three concepts

| Concept         | Meaning                                                                                                                                                        |
| :-------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Baseline**    | An approved deployed application with registered service addresses and a readiness check. It can represent `main`, a release, or another reference deployment. |
| **Override**    | A replacement container image for an approved service. Envy deploys it in a temporary namespace.                                                               |
| **Composition** | A temporary selection of baseline bindings and zero to three overrides, with an expiry time. HTTP selections also receive a URL.                               |

The preview ingress sets `baggage: composition=<id>`. Applications must forward that header on downstream HTTP calls. The selected mesh uses it to select the matching override; calls without matching composition context use the baseline.

Existing OpenTelemetry instrumentation can provide this propagation when configured for W3C Baggage on both incoming handlers and outgoing clients. See the [routing contract](/reference/routing/) for an example.

## What stays shared

Unchanged services, databases, caches, and external dependencies remain shared. **Writes from a preview can change baseline data.** Envy provides request routing and separate override workloads; it does not create an independent copy of application state.

This model suits integration testing against an existing reference application. Tests that require independent databases or destructive migrations need separate data arrangements. Optional [Google Pub/Sub isolation](/guides/pubsub-isolation/) provides filtered preview subscriptions when applications and baseline subscriptions implement its contract; other messaging systems remain shared. Read [Sharing & Isolation](/overview/sharing-semantics/) before onboarding an application.

## Preview lifecycle

1. Create a composition with approved images and a TTL (8 hours by default).
2. For HTTP components, wait until workload readiness, routing, and the declared ingress check succeed. For endpoint-free Jobs, wait for the reported execution lifecycle.
3. Run your own functional tests against the preview URL or inspect the Job outcome. Readiness confirms the configured check, not every application behavior.
4. Update images in place or request teardown. The reconciler also cleans up expired compositions.

An HTTP URL is allocated when creation is accepted. Time to readiness or completion depends on image pulls, workload startup, routing where required, and verification.
